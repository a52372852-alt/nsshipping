# 프로젝트명

NS Shipping Converter

# 목표

쿠팡, 네이버 스마트스토어, 토스쇼핑에서 다운로드한 주문 Excel 파일을 웹에 업로드하면 플랫폼을 자동으로 판별하고 주문 데이터를 정규화한 뒤, 롯데택배 송장 업로드용 Excel 파일로 변환하여 다운로드할 수 있는 웹 서비스를 구현한다.

이 프로젝트는 단순한 테스트 페이지가 아니라 실제 업무에서 사용할 수 있는 완성도 높은 웹 서비스로 만든다.

가장 중요한 UX 원칙은 다음과 같다.

**사용자는 첫 페이지 하나에서 모든 작업을 완료할 수 있어야 한다.**

별도의 변환 페이지로 이동하지 않는다.

랜딩페이지와 실제 변환 도구를 하나의 메인 페이지에 자연스럽게 통합한다.

# 1. 기술 스택

다음 기술을 우선 사용한다.

- Next.js 최신 안정 버전
- TypeScript
- React
- Tailwind CSS
- shadcn/ui
- Lucide Icons
- SheetJS(xlsx) 또는 ExcelJS
- 클라이언트 기반 Excel 분석/변환 우선
- 필요하지 않은 경우 DB 사용 금지
- 필요하지 않은 경우 로그인 기능 구현 금지

주문자 이름, 전화번호, 주소 등의 개인정보가 포함되므로 MVP에서는 가능한 한 업로드한 Excel을 서버로 전송하거나 저장하지 않고 브라우저에서 처리한다.

# 7. 내부 공통 주문 모델

각 플랫폼 데이터를 곧바로 롯데택배 형식으로 변환하지 않는다.

먼저 내부 공통 Order 타입으로 정규화한다.

예:

```ts
export interface NormalizedOrder {
  platform: "coupang" | "smartstore" | "toss";
  sourceFileName: string;

  orderId: string;
  productOrderId?: string;

  receiverName: string;
  receiverPhone1: string;
  receiverPhone2?: string;

  postalCode: string;
  address: string;

  productName: string;
  optionName?: string;

  quantity: number;

  deliveryMessage?: string;
}
```

플랫폼별 parser와 롯데택배 exporter를 완전히 분리한다.

구조 예:

```text
src/
  lib/
    excel/
      detectPlatform.ts

      parsers/
        coupang.ts
        smartstore.ts
        toss.ts

      exporters/
        lotte.ts

      validators/
        orderValidator.ts

      transforms/
        normalizePhone.ts
        productNameRules.ts

  types/
    order.ts
```

# 8. 쿠팡 → 공통 Order 매핑

다음 실제 Excel 컬럼명을 기준으로 처리한다.

- 주문번호 → orderId
- 수취인이름 → receiverName
- 수취인전화번호 → receiverPhone1
- 우편번호 → postalCode
- 수취인 주소 → address
- 등록상품명 → productName
- 등록옵션명 → optionName
- 구매수(수량) → quantity
- 배송메세지 → deliveryMessage

주의:

컬럼명이 일부 달라질 가능성에 대비하여 alias 처리를 허용한다.

하지만 없는 컬럼을 임의로 추측하여 잘못 매핑하지 않는다.

---

# 9. 스마트스토어 → 공통 Order 매핑

- 주문번호 → orderId
- 상품주문번호 → productOrderId
- 수취인명 → receiverName
- 수취인연락처1 → receiverPhone1
- 수취인연락처2 → receiverPhone2
- 우편번호 → postalCode
- 통합배송지 → address
- 상품명 → productName
- 옵션정보 → optionName
- 수량 → quantity
- 배송메세지 → deliveryMessage

주소는 `통합배송지`를 우선 사용한다.

통합배송지가 비어있는 경우에만 기본배송지 + 상세배송지를 안전하게 결합한다.

# 10. 토스쇼핑 → 공통 Order 매핑

- 주문번호 → orderId
- 주문상품번호 → productOrderId
- 수령인명 → receiverName
- 수령인 연락처 → receiverPhone1
- 우편번호 → postalCode
- 배송지 → address
- 상품명 → productName

- 주문건수 → quantity

실제 샘플 Excel의 정확한 헤더명이 다를 경우 샘플 파일을 Source of Truth로 삼는다.

# 12. 롯데택배 매핑

NormalizedOrder를 다음과 같이 변환한다.

- orderId → 주문번호
- senderName → 보내는사람(지정)
- senderPhone → 전화번호1(지정)
- receiverName → 받는사람
- receiverPhone1 → 전화번호1
- receiverPhone2 → 전화번호2
- postalCode → 우편번호
- address → 주소
- productName → 상품명1
- optionName → 상품상세1
- quantity → 수량(A타입)
- deliveryMessage → 배송메시지

다음 값은 설정값으로 처리한다.

보내는사람(지정):
`엔에스벨류몰`

운임구분:
`신용`

운송장번호:
빈 값

운임:
빈 값

발송인 전화번호는 설정 화면에서 사용자가 지정할 수 있게 한다.

코드에 개인정보성 전화번호를 하드코딩하지 않는다.

# 13. 매우 중요한 데이터 처리 규칙

다음을 반드시 지킨다.

## 주문번호

Excel에서 숫자로 자동 변환하지 않는다.

무조건 문자열 취급한다.

큰 주문번호가 scientific notation으로 변환되지 않게 한다.

예:

잘못된 결과:

`1.31033E+13`

올바른 결과:

`12345678901234`

---

## 전화번호

무조건 문자열 처리한다.

앞자리 0을 삭제하지 않는다.

안심번호를 임의 변환하지 않는다.

예:

`0504-3532-9549`

그대로 유지한다.

---

## 우편번호

무조건 문자열 처리한다.

앞자리 0을 유지한다.

# 15. 중복 주문 검사

여러 파일을 올렸을 때 같은 주문이 중복될 수 있다.

다음 조합으로 중복 여부를 판단할 수 있도록 설계한다.

우선:

platform + orderId + productOrderId

productOrderId가 없는 경우:

platform + orderId + receiverName + productName

중복을 자동 삭제하기 전에 사용자에게 표시한다.

예:

`중복 의심 주문 2건`

사용자가 포함/제외할 수 있게 한다.

# 16. 상품명 자동 치환

업무상 롯데택배에는 쇼핑몰의 긴 상품명 대신 짧은 상품명을 넣고 싶을 수 있다.

상품명 치환 기능을 제공한다.

예:

```text
NS 극세사 블랭킷 무릎 담요
→ 블랭킷

NS HOME A-CLASS BLANKET
→ 블랭킷
```

UI:

`상품명 규칙`

원본 상품명 | 변환 상품명

규칙 추가 버튼 제공.

localStorage에 저장하여 다음 방문에서도 유지할 수 있게 한다.

서버 DB는 필요 없다.

# 21. Excel 파일 생성 품질

롯데택배 샘플 Excel을 Source of Truth로 삼는다.

가능하면 샘플 양식의:

- 컬럼명
- 컬럼 순서
- 셀 형식
- 텍스트 형식

을 최대한 유지한다.

불필요한 추가 sheet를 만들지 않는다.

Excel 출력이 롯데택배 프로그램에서 바로 업로드 가능한 형식이어야 한다.

# 22. 샘플 파일

프로젝트에 다음 샘플 Excel을 보관한다.

예:

```text
samples/
  coupang.xlsx
  smartstore.xlsx
  toss.xlsx
  lotte-template.xlsx
```

제공된 실제 Excel 파일을 분석하여 parser와 exporter 테스트에 사용한다.

파일 내용과 코드가 충돌하는 경우 추측하지 말고 실제 샘플 Excel 구조를 Source of Truth로 사용한다.

# 24. 빈 화면 상태

파일을 올리지 않았을 때도 화면이 허전해 보이지 않게 한다.

Drop Zone 아래에 다음 메시지를 표시한다.

`업로드한 주문 데이터는 브라우저에서 처리되며 서버에 저장하지 않습니다.`

# 25. 오류 UX

지원하지 않는 파일을 넣은 경우:

`지원하지 않는 주문 양식입니다.`

그리고 감지한 시트/헤더 일부를 개발자 콘솔에만 표시하지 말고 사용자에게 이해 가능한 수준으로 알려준다.

예:

`쿠팡, 스마트스토어 또는 토스쇼핑 주문 파일인지 확인해주세요.`

Excel 파일 자체가 깨진 경우:

`Excel 파일을 읽을 수 없습니다.`

비밀번호 파일:

`암호화된 Excel 파일은 현재 지원하지 않습니다. 암호를 해제한 뒤 다시 업로드해주세요.`

# 26. 개인정보 보호

이 서비스는 주문자 개인정보를 다룬다.

첫 페이지에 다음 내용을 간결하게 표시한다.

`파일은 브라우저에서 처리됩니다.`

`업로드된 주문정보를 서버에 저장하지 않습니다.`

실제 구현도 이 문구와 일치해야 한다.

서버로 파일을 업로드하면서 위 문구를 표시하면 안 된다.

# 29. 테스트

샘플 Excel을 사용하여 다음 테스트를 만든다.

## 플랫폼 감지

- 쿠팡 파일 → coupang
- 스마트스토어 → smartstore
- 토스 → toss

## 주문 parsing

각 플랫폼의 첫 번째 실제 주문이 올바르게 NormalizedOrder로 변환되는지 검사.

## 롯데 exporter

NormalizedOrder를 넣었을 때 롯데택배 18개 컬럼이 정확한 순서로 생성되는지 검사.

## 데이터 보존

- 주문번호 문자열 유지
- 전화번호 앞자리 0 유지
- 우편번호 앞자리 0 유지

# 32. 매우 중요한 작업 원칙

기능을 임의로 축소하지 않는다.

샘플 Excel 파일을 분석하지 않고 헤더를 추측하지 않는다.

Excel 관련 구현은 실제 제공된 파일을 기준으로 검증한다.

첫 페이지에서 변환 업무 전체를 완료해야 한다.

대시보드처럼 여러 페이지로 쪼개지 않는다.

사용자가 처음 방문했을 때 3초 안에 무엇을 하는 서비스인지 이해할 수 있어야 한다.

사용자가 설명서를 읽지 않아도 파일을 올리고 결과를 받을 수 있어야 한다.

랜딩페이지와 업무도구가 따로 노는 느낌이 없어야 한다.

디자인은 실제 유료 SaaS 서비스로 출시할 수 있는 수준으로 다듬는다.

임시 placeholder UI로 완료 처리하지 않는다.

모든 기능 구현 후:

```bash
npm run lint
npm run build
```

를 실행하고 발생하는 오류를 모두 수정한다.

완성 후 README.md에 다음 내용을 정리한다.

- 프로젝트 소개
- 실행 방법
- 지원 플랫폼
- Excel 변환 구조
- 샘플 파일 위치
- 새로운 마켓 추가 방법
- 개인정보 처리 방식

그리고 구현 완료 후 실제 샘플 Excel 각각을 프로그램으로 읽어보고 롯데택배 Excel 생성까지 테스트하여 결과를 확인한다.
